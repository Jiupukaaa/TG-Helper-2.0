# TG Helper

Личный Telegram-ассистент без ИИ: заметки и напоминания. Основной интерфейс — Telegram; веб-страница — просто индикатор "жив/не жив".

Стек: TypeScript, Next.js (App Router), Prisma, PostgreSQL (Neon), grammy (Telegram Bot API), GitHub Actions (регулярный запуск проверки напоминаний).

Это отдельный, самостоятельный проект. Он не использует и не затрагивает какой-либо другой существующий проект (например, DonationHub) — ни код, ни базу данных, ни инфраструктуру.

---

## 1. Что нужно установить локально

- Node.js 18.18+ (проверялось на 22.x)
- npm
- Доступ к PostgreSQL базе для разработки (см. ниже — можно локальный Postgres или тестовый проект в Neon)

## 2. Установка

```bash
npm install
```

`postinstall` автоматически выполнит `prisma generate`.

## 3. Переменные окружения

Скопируйте пример и заполните:

```bash
cp .env.example .env
```

| Переменная | Назначение |
|---|---|
| `TELEGRAM_BOT_TOKEN` | Токен бота от [@BotFather](https://t.me/BotFather) |
| `TELEGRAM_WEBHOOK_SECRET` | Придуманная вами строка-секрет для проверки, что webhook действительно вызывает Telegram (см. §6) |
| `ALLOWED_TELEGRAM_IDS` | Ваш числовой Telegram ID (можно узнать у [@userinfobot](https://t.me/userinfobot)), через запятую если пользователей несколько |
| `DATABASE_URL` | Строка подключения к Postgres (Neon или локальный) |
| `CRON_SECRET` | Придуманная вами строка-секрет для защиты cron-эндпоинта (см. §7) |

Пустой `ALLOWED_TELEGRAM_IDS` означает "доступ запрещён всем" — это осознанный безопасный дефолт, а не баг.

## 4. База данных и Prisma

Файл `prisma/schema.prisma` уже готов (модели `User`, `Note`, `Reminder`, `Session`). Реальная база и миграции **не подключались и не выполнялись** — это шаг, который вы делаете сами.

Локально (например, с локальным Postgres или тестовой Neon-веткой):

```bash
npx prisma migrate dev --name init
```

Это создаст таблицы и сгенерирует клиент. Посмотреть содержимое базы:

```bash
npx prisma studio
```

2. Вставьте его в `DATABASE_URL` (в `.env` локально и/или в Environment Variables на Vercel).

## 5. Локальный запуск

```bash
npm run dev
```

Откроется `http://localhost:3000` — статус-страница. Сам бот через `dev`-сервер работать не будет, пока Telegram не сможет достучаться до webhook (см. ниже про туннель для локальной проверки).

### Проверка бота локально (до деплоя)

Telegram webhook требует публичный HTTPS-адрес. Для локальной проверки без деплоя на Vercel можно временно прокинуть локальный сервер наружу (например, `ngrok http 3000`) и один раз указать полученный URL в `setWebhook` (см. §6) — это тестовый, а не постоянный вариант.

## 6. Настройка Telegram webhook (после деплоя)

Когда проект задеплоен на Vercel и у вас есть публичный URL:

```bash
curl -X POST "https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/setWebhook" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://<ваш-домен>/api/telegram/webhook",
    "secret_token": "<TELEGRAM_WEBHOOK_SECRET>"
  }'
```

Telegram будет присылать этот же секрет в заголовке `X-Telegram-Bot-Api-Secret-Token` на каждый запрос — webhook-эндпоинт сверяет его и отвечает `401`, если секрет не совпадает или отсутствует.

Проверить текущий статус webhook:

```bash
curl "https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/getWebhookInfo"
```

Удалить webhook (если нужно вернуться к локальному тестированию через polling или ngrok):

```bash
curl "https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/deleteWebhook"
```

## 7. Регулярный запуск проверки напоминаний — GitHub Actions

**Vercel Cron больше не используется** (на плане Vercel Hobby минимальный шаг Vercel Cron — раз в сутки, что не подходит для системы напоминаний). Сам API-эндпоинт `/api/cron/reminders` никуда не делся и продолжает работать на Vercel как обычный route — просто дёргает его теперь не Vercel, а GitHub Actions.

Файл `.github/workflows/trigger-reminders.yml` каждые 5 минут отправляет:

```
POST https://<ваш-домен>/api/cron/reminders
Authorization: Bearer <CRON_SECRET>
```

Чтобы это заработало, в вашем GitHub-репозитории нужно один раз настроить:

1. **Секрет с ключом авторизации** — `Settings → Secrets and variables → Actions → Secrets → New repository secret`:
   - имя: `CRON_SECRET`
   - значение: **то же самое**, что установлено в Vercel Environment Variables (`CRON_SECRET` не является новым секретом — это тот же самый, что уже используется эндпоинтом).
2. **Переменная с адресом продакшена** — `Settings → Secrets and variables → Actions → Variables → New repository variable` (это не секрет, просто URL, но чтобы не хардкодить домен в workflow-файле):
   - имя: `TG_HELPER_URL`
   - значение: ваш продовый URL, например `https://tg-helper.vercel.app` (без слэша на конце — но лишний слэш workflow тоже перенесёт корректно).

Проверить вручную, не дожидаясь расписания: вкладка **Actions** → workflow **Trigger reminders check** → **Run workflow**.

**Почему интервал 5 минут безопасен**: эндпоинт захватывает просроченные напоминания одним атомарным SQL-запросом (`UPDATE ... FOR UPDATE SKIP LOCKED`), так что параллельные или перекрывающиеся запуски (в том числе если GitHub Actions выполнит расписание с задержкой) не могут забрать одно и то же напоминание дважды одновременно. Порог реанимации "зависших" записей — 5 минут, а сама функция ограничена 60 секундами выполнения (`maxDuration`), так что реальный прогон физически не может длиться дольше этого порога. Логика в `remindersService.ts` и `route.ts` не менялась.

Особенность именно GitHub Actions (не баг, а как это устроено у GitHub): scheduled-запуски могут выполняться с небольшой задержкой в периоды высокой нагрузки на инфраструктуру GitHub — это может немного сдвинуть момент доставки напоминания, но не создаёт риска дублей.

## 8. Развёртывание (шаги, которые выполняете вы сами)

Ничего из этого не выполнялось автоматически — ни GitHub, ни Neon, ни Vercel не подключались.

1. **GitHub** — создайте репозиторий, запушьте код из этого проекта.
2. **Neon** — создайте проект и базу, получите `DATABASE_URL`, выполните `npx prisma migrate deploy`.
3. **Vercel** — импортируйте репозиторий, добавьте все переменные из `.env.example` в Environment Variables, задеплойте.
4. **Telegram webhook** — выполните команду из §6 с продовым URL.
5. **GitHub Actions** — добавьте secret `CRON_SECRET` (то же значение, что в Vercel) и переменную `TG_HELPER_URL` с продовым доменом (см. §7). Без этого шага напоминания не будут отправляться — webhook и заметки при этом продолжат работать.
6. Отправьте `/start` боту в Telegram.

## 9. Архитектура обработки напоминаний (кратко)

- Время хранится в базе **всегда в UTC** (`Reminder.dueAt`). Конвертация в локальное время пользователя происходит только на входе (при создании) и на выходе (при показе/отправке) — см. `src/lib/time.ts`.
- Часовой пояс задаётся вручную командой `/settimezone Europe/Amsterdam` (IANA-имя). Геолокация не используется.
- Статусы напоминания: `PENDING → PROCESSING → SENT | FAILED`.
- Эндпоинт `/api/cron/reminders` (регулярно вызывается через GitHub Actions, см. §7) атомарно "захватывает" просроченные напоминания одним SQL-запросом (`UPDATE ... FOR UPDATE SKIP LOCKED`), что защищает от двойной обработки при параллельных/повторных запусках. Зависшие в `PROCESSING` дольше 5 минут записи (например, из-за упавшей функции) снова становятся доступны для захвата.
- **Честно об ограничениях**: если функция упадёт ровно между успешной отправкой в Telegram и записью статуса `SENT` в базу, повторный прогон cron отправит напоминание повторно. Это фундаментальное ограничение (Telegram API и база — независимые системы без общей транзакции), и для личного MVP-бота осознанно принято как редкий крайний случай, а не решено сложной инфраструктурой (outbox/saga), что противоречило бы требованию не усложнять проект.
- Ошибки Telegram делятся на постоянные (403 — бот заблокирован пользователем → сразу `FAILED`) и временные (rate limit, 5xx → до 3 повторных попыток, затем `FAILED`).

## 10. Проверка (ручной чек-лист для этапа 3)

Реальную базу и бота вы подключаете сами — ниже сценарии для проверки после этого:

- [ ] `/start` — создаётся пользователь, приходит приветствие с меню.
- [ ] Попытка использовать бота с чужого Telegram ID (не в `ALLOWED_TELEGRAM_IDS`) — получает отказ, никакие данные не создаются.
- [ ] `/notes` → "➕ Новая заметка" → ввод текста → заметка сохраняется, приходит подтверждение с ID.
- [ ] "📋 Все заметки" — показывает список; `/note <id>` открывает конкретную.
- [ ] "✏️ Изменить" → новый текст → заметка обновляется.
- [ ] "🗑 Удалить" → подтверждение → заметка удаляется.
- [ ] Попытка открыть/изменить/удалить чужую заметку по ID (от другого пользователя) — не находится (проверка `ownerId`).
- [ ] `/settimezone Europe/Amsterdam` — устанавливается; `/settimezone НеСуществующаяЗона` — отклоняется с понятной ошибкой.
- [ ] Попытка создать напоминание до настройки таймзоны — бот просит сначала выполнить `/settimezone`.
- [ ] Создание напоминания: текст → дата в неверном формате → бот просит повторить, не сбрасывая текст. Затем корректная дата в будущем → напоминание создаётся, время показывается в локальной зоне.
- [ ] Создание напоминания с датой в прошлом — отклоняется, предлагается ввести другую дату (сессия не сбрасывается).
- [ ] "❌ Отмена" на любом шаге — сценарий прерывается, данные не сохраняются.
- [ ] Ручной запуск workflow (`Actions → Trigger reminders check → Run workflow`) завершается успешно (зелёная галочка, без 401/ошибок в логе шага).
- [ ] Напоминание с наступившим временем действительно приходит в Telegram при следующем срабатывании workflow (по расписанию или вручную).
- [ ] Повторный ручной запуск workflow сразу после успешной отправки — то же напоминание не отправляется повторно (статус уже `SENT`).
- [ ] Искусственно "подвесить" напоминание в `PROCESSING` (обновить строку вручную через Prisma Studio, выставив старый `processingStartedAt`) — следующий запуск workflow забирает его снова.
- [ ] Ввод неизвестной команды — бот отвечает про неизвестную команду и не падает.

### Автоматизированные тесты

В этой версии автоматические тесты не включены (не было явного требования в ТЗ, а добавление тестового фреймворка ради галочки увеличило бы объём проекта без необходимости). Если нужно — следующим шагом можно добавить `vitest` с юнит-тестами на `src/lib/time.ts` (конвертация дат) и `src/services/*` (валидация, права доступа), это наиболее ценные для покрытия места.

## 11. Известные ограничения MVP

- Нет пагинации в списках заметок/напоминаний — для личного использования с небольшим количеством записей это не критично, но при росте объёма стоит добавить.
- Дубли при отправке напоминаний в редком крайнем случае (см. §9) не устранены полностью — это осознанный компромисс для MVP.
- Запуск проверки напоминаний зависит от GitHub Actions scheduler, который может выполняться с задержкой в периоды высокой нагрузки на инфраструктуру GitHub — точность доставки напоминаний ограничена этим (обычно задержка небольшая, но гарантии "ровно в 5 минут" GitHub не даёт).
